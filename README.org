#+title: My .files

This repository contains my personal configuration files (dotfiles) for various applications and tools.

** What is a Dotfile?
Dotfiles are configuration files for Unix-based systems that start with a dot (.), such as:

~/.gitconfig

These files store user preferences and settings for different command-line tools, text editors, and system behaviors.

** Installation
To set up these dotfiles on a new system, clone the repository and run
the install script:

#+begin_src sh
git clone https://github.com/unipro/dotfiles.git ~/dotfiles
cd ~/dotfiles
./install.sh
#+end_src

=install.sh= *copies* the managed files into =$HOME=, =~/.config= and
=~/.claude= (it does not create symlinks). A target that already matches
the source is left alone entirely; otherwise it is moved aside to
=<file>.backup= first, and a pre-existing =.backup= is never overwritten —
so your original files stay safe and re-running is idempotent. No backup
is made when the target is a version this repository shipped, since git
history already holds it.

Shell startup files are the exception to "copy": see [[#startup-files][Startup files
you already have]].

The =claude= component is the one exception: it syncs *both ways* rather
than only repo → home. See [[#claude-code][Claude Code]] below.

*** Installing a subset
With no arguments =install.sh= installs everything. To replace only part
of the configuration, name the components you want:

#+begin_src sh
./install.sh --list       # show the available components
./install.sh doom         # only ~/.config/doom
./install.sh bash zsh     # both shells
./install.sh shellenv     # reinstall the env generator and re-run it
./install.sh bash git     # only the shell and Git configs
./install.sh all          # explicit alias for "everything"
#+end_src

| Component      | Installs                                                                    |
|----------------+-----------------------------------------------------------------------------|
| =bash=         | =~/.bashrc=, =~/.bash_profile=, =~/.profile=, =~/.config/bash/=             |
| =zsh=          | =~/.zshrc=, =~/.config/zsh/= (fallback shell)                                |
| =shellenv=     | =~/.local/bin/mkshellenv=, and the env files it generates for both shells    |
| =git=          | =~/.gitconfig=, with =~/.gitconfig.local= inlined                           |
| =clang-format= | =~/.clang-format=                                                           |
| =doom=         | =~/.config/doom/=                                                           |
| =ghostty=      | =~/.config/ghostty/=                                                        |
| =claude=       | =~/.claude/CLAUDE.md= (two-way sync, newest side wins)                       |

Unknown component names are rejected before anything is copied, and the
components always run in the order listed above regardless of argument
order.

** Managing Updates
Pull the latest changes and re-run the install script to propagate
them (since files are copied, not symlinked, a =git pull= alone does
not update the installed copies):

#+begin_src sh
cd ~/dotfiles
git pull origin main
./install.sh
#+end_src

If you only changed one area, re-install just that component — e.g.
=./install.sh doom= after editing =dotconfig/doom/config.el=.

To contribute your own changes back, edit the files in the repository,
then commit and push:

#+begin_src sh
git add .
git commit -m "Update configurations"
git push origin main
#+end_src

** Local Git Configuration
To set system-specific Git configurations, you can use `~/.gitconfig.local`. This file is not included in the repository and should be created separately for each system.

Example content of `~/.gitconfig.local`:

#+begin_src ini
[user]
    name = Byungwan Jun
    email = unipro.kr@gmail.com

[credential]
    helper = osxkeychain
#+end_src

** Shell Configuration
bash is the daily driver; zsh is kept working as a fallback (it is
macOS's default shell, so things do land in it). Both read the same
machine-specific environment generated by =mkshellenv=, and the bash
configuration is split into two layers, both cross-platform (macOS and
Linux):

*** Login entry points (installed to =$HOME=)
These are the standard bash startup files, kept as a single
cross-platform version each and installed into =$HOME= by =install.sh=
(see [[#startup-files][Startup files you already have]] for what happens to a file
that is already there):

- =.bash_profile= : login shells; bootstraps Homebrew, then sources
  =~/.profile= and =~/.bashrc=
- =.profile=      : POSIX login setup (private =bin= PATH, cargo env)
- =.bashrc=       : interactive shells; history, prompt, =ls= colors,
  then sources =~/.config/bash/init=

OS differences (Homebrew vs Linuxbrew, =ls -G= vs =ls --color=auto=,
=/etc/bashrc= vs =/etc/bash.bashrc=) are handled inline via =$OSTYPE=,
so the same files work on both platforms.

*** Reusable scripts (installed to =~/.config/bash/=)
=install.sh= installs the following into =~/.config/bash/=, from
=dotconfig/bash/= in the XDG config tree:

- =init=       : entry point sourced from =~/.bashrc=; loads the rest
- =aliases=    : interactive aliases and helper functions
- =completion= : loads the snippets in =~/.config/bash/completion.d/=

*** Startup files you already have
:PROPERTIES:
:CUSTOM_ID: startup-files
:END:
=install.sh= will not clobber a =~/.bashrc=, =~/.bash_profile=,
=~/.profile= or =~/.zshrc= it did not write — a company image, a distro
default, or another dotfiles manager keeps working. For each of those
files, in order:

1. *absent* → the repository's copy is installed
2. *carries the =dotfiles-managed= marker*, or matches a version this
   repository has committed → it is ours, so it is brought up to date
3. *=--force-rc= given* → treated as ours anyway
4. *already sources the target* → left exactly as it is
5. *anything else* → it is yours: the loader block is *appended* and
   nothing else in the file is touched (the original is backed up first)

What gets appended is just the hook:

#+begin_src sh
# Added by the dotfiles install script -- load the shell configuration in
# ~/.config. Delete this block to unhook it.
if [ -f "$HOME/.config/bash/init" ]; then
    . "$HOME/.config/bash/init"
fi
#+end_src

so everything in =~/.config/bash/= (and =~/.config/zsh/=) still reaches
the shell, while the surrounding file stays yours. =~/.bash_profile= is
wired to =~/.bashrc= rather than to the init script: macOS terminals
start login shells, which read only =.bash_profile=, so without that hop
the =.bashrc= wiring would never fire. =~/.profile= carries no hook, so a
foreign one is simply left alone.

Step 2 consults the history, not just the marker, so a copy installed
before the marker existed is still recognized; otherwise it would look
foreign, be found already wired, and never see another update. When a
file really is yours but you want the managed version anyway:

#+begin_src sh
./install.sh -f bash        # replace unmarked startup files
rm ~/.bashrc && ./install.sh bash   # or start from scratch
#+end_src

*** The env generator (=mkshellenv=)
=bin/mkshellenv= probes the machine — Homebrew prefix and kegs, JDK,
pyenv, fnm, Go, GStreamer … — and writes what it finds to
=~/.config/bash/env= (bash) and =~/.config/zsh/env= (zsh). Both =env=
files and a private =~/.config/bash/private= (for machine-local
secrets/aliases) are git-ignored and never committed.

It installs to =~/.local/bin/mkshellenv=, which =~/.profile= puts on
PATH, so re-running it after installing a new toolchain is just:

#+begin_src sh
mkshellenv
#+end_src

Two deliberate choices there: it lives on PATH rather than in the XDG
config tree because it is a command, not a config file; and it is named
=mkshellenv= rather than =mkenv= because =~/.local/bin= sits at the front
of PATH, where a generic name would silently shadow (or be shadowed by) a
tool installed later by brew or =npm -g=.

Internally the machine probing is shell-agnostic and only the last step
knows about shells: one =emit_env <shell> <outfile>= function, called
once for bash and once for zsh. The differences between the two amount to
fnm's =--shell= flag, nvm's bash-only completion, and the shell argument
the pyenv and direnv hooks take.

=./install.sh shellenv= reinstalls the generator and runs it; every other
component leaves the =env= files alone.

*** zsh (fallback shell)
The same two layers, kept deliberately thin:

- =.zshrc=            : bootstraps Homebrew, sources =~/.profile=, sets
  history/prompt/=ls= aliases, then sources =~/.config/zsh/init=
- =~/.config/zsh/init= : runs =compinit=, loads =~/.config/zsh/env=, and
  reuses bash's =aliases= and =private= files unless a zsh-specific
  =~/.config/zsh/aliases= (or =private=) exists

Unlike bash there is no =~/.zprofile=: macOS terminals do start login
shells, but a zsh spawned from another shell is interactive-only, and
that is exactly the case where PATH still has to work — so everything
goes in =~/.zshrc=.

*** Node.js (fnm)
Node versions are managed by [[https://github.com/Schniz/fnm][fnm]] (=brew install fnm=), which
=mkshellenv= detects and wires into both shells:

#+begin_src sh
eval "$(fnm env --use-on-cd --shell bash)"   # or --shell zsh
#+end_src

The =eval= *line* is written out rather than its output, because =fnm
env= mints a per-session =FNM_MULTISHELL_PATH= that dies with the shell
that created it. =--use-on-cd= switches versions on entering a directory
with =.node-version=, =.nvmrc= or a =package.json= =engines.node=.

Pick a default so every new shell has a node:

#+begin_src sh
fnm install --lts
fnm default lts-latest
mkshellenv               # picks up ~/.local/share/fnm/aliases/default/bin
#+end_src

That =default= alias also goes on PATH statically, as a stable fallback
behind the per-session directory. Both live in the generated =env= file,
which only interactive shells read — a cron job or a GUI-launched app
gets no node from here.

nvm is still detected as a fallback for machines that have it, but fnm
wins when both are present; running both would leave two managers
fighting over PATH. Homebrew's =node@22= keg is deliberately left off
PATH for the same reason.

** Doom Emacs
The [[https://github.com/doomemacs/doomemacs][Doom Emacs]] configuration lives in =dotconfig/doom/= and is
installed to =~/.config/doom/= by =install.sh=.

- =init.el=     : enabled Doom modules
- =config.el=   : personal configuration
- =packages.el= : extra packages
- =bin/=        : helper scripts

Machine-local overrides go in =~/.config/doom/local.el= (and
=custom.el=); both are git-ignored and never committed. After changing
=init.el= or =packages.el=, run =doom sync=.

** Claude Code
:PROPERTIES:
:CUSTOM_ID: claude-code
:END:
[[https://claude.com/claude-code][Claude Code]] keeps its user-level configuration in =~/.claude= rather
than the XDG tree, so it gets its own source directory =dotclaude/=
instead of living under =dotconfig/=:

- =CLAUDE.md= : global instructions loaded into every session on this
  machine

Everything else in =~/.claude= is runtime state that Claude Code
generates and owns (=sessions/=, =projects/=, =history.jsonl=, caches,
=settings.json=). =install.sh= only looks at the files present in
=dotclaude/=, so that state is never read, written, or pulled into the
repository. To manage another file, add it to =dotclaude/= and it is
picked up automatically.

*** Two-way sync
The global rules get edited from inside a Claude Code session about as
often as they get edited in the repository, so =./install.sh claude=
syncs rather than overwrites — for each file in =dotclaude/=:

1. contents identical → nothing happens
2. =~/.claude= copy is newer → it is copied *into the repository*
3. =dotclaude/= copy is newer → it is installed to =~/.claude= (with the
   usual =<file>.backup=)

#+begin_src sh
./install.sh claude       # reconcile both sides, newest wins
git diff dotclaude/       # review whatever got pulled in
#+end_src

One caveat: Git restamps the files it checks out, so a file touched by
=git pull= looks newer than an older local edit and wins. Run
=./install.sh claude= *before* pulling to capture local edits first.
